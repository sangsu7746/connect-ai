## 2단계 — 무장 전 최종 리허설 (여전히 DRY-RUN)

`GLOBAL_DRY_RUN=1` 그대로. 실제 채널 1개만 켜고 전 구간 확인:
```bash
python -m uvicorn app:app --port 8010      # 접수+승인+스케줄러 상주
```
- 캠페인 실행(오케스트레이터) → `http://127.0.0.1:8010/approvals` 에서 전단·캡션 확인 → 승인 → **로그에 `[DRY-RUN][band] POST …`** 뜨는지 확인.
- 접수폼 `http://127.0.0.1:8010/intake` 제출 → 대출앱 loans.json 반영 확인.

여기까지 문제 없으면 실발행 준비 완료.

## 3단계 — 실발행 무장 (버너 채널부터)

1. **버너/테스트 채널 준비** — 내가 소유한 테스트 밴드(또는 부계정) 1개.
2. `.env` → `GLOBAL_DRY_RUN=0`, `DAILY_POST_LIMIT=2` (낮게 시작).
3. **로그인 세션 만들기** — 비밀번호는 시스템에 넣지 않습니다.

   ```bash
   python login.py --check                                  # 저장된 세션 목록·나이 확인
   python login.py band     --account 내네이버아이디          # 창에서 직접 로그인
   python login.py facebook --account 내이메일@example.com
   python login.py kakao                                     # 안내만(로그인 불필요)
   ```

   - 브라우저 창이 열리면 **사장님이 직접** 아이디·비밀번호를 입력하고 2FA/캡차를 통과합니다.
     스크립트는 "로그인됐는지"만 감지해 **세션(쿠키)을 저장**합니다.
   - 이후 시스템은 **비밀번호 없이** 이 세션으로 발행합니다 (`adapter.login()` 인자 없이 호출).
   - 세션이 만료되면 발행 시 "저장된 세션 만료" 로그가 뜨고, 위 명령을 다시 실행하면 됩니다.
   - 카카오는 **PC 카카오톡을 로그인 상태로 열어두기만** 하면 됩니다(AHK가 창을 조작).
4. 버너 채널로 캠페인 → 승인 → **실제 1건 게시** → 밴드/페북/카톡에서 눈으로 확인.
5. 이상 없으면 실제 소비자 채널로 **한 채널씩** 확대(밴드 → 페북 → 카카오), 상한을 서서히 올림.

## 카카오 실전송 주의 (특히 취약)

- 데스크톱 카톡 창이 **열려 있고 로그인**돼 있어야 함. AutoHotkey가 창을 제어.
- 전송 중 **다른 창 포커스 뺏기 금지**(오전송 위험). 해상도/카톡 업데이트 시 셀렉터 깨질 수 있음.
- 어댑터가 **방 이름 검증**을 하지만, 켜는 방은 **정확한 이름**으로. 첫 전송은 테스트 방으로.

## 쓰레드 답글 자동광고 — 점화 순서

> 위 0~3단계(밴드/페북/카카오)와는 **별개의 채널**입니다. 아래 순서를 건너뛰지 말고
> 그대로 따르세요 — 특히 **3단계(마크업 검증)와 5단계(골든셋 실측)는 생략하면 안 됩니다.**
> 이 파이프라인의 파서는 지금까지 합성(가짜) 데이터로만 검증됐고, 자동 발행 임계값도
> 아직 실측 근거가 없는 기본값(90점)입니다.

### 1. 세션 만들기
```bash

```
- 창이 뜨면 **사장님이 직접** 로그인합니다(2FA·캡차 포함, 스크립트는 자동 로그인을
  시도하지 않습니다 — 자동 로그인 시도 자체가 탐지 신호가 되기 쉽습니다).
- 로그인을 마치고 콘솔에서 Enter 를 치면, 스크립트가 **로그인이 실제로 됐는지 확인한
  뒤에만** 쿠키를 저장합니다. 확인이 안 되면 "로그인 상태가 확인되지 않았습니다"라고
  뜨고 쿠키는 저장되지 않습니다 — 다시 시도하세요.

### 2. 준비 상태 점검
```bash

```
`[8] 쓰레드 답글 자동광고 (threads)` 절에서 아래 4개 항목이 전부 `[OK]` 인지 확인:

### 3. 마크업 검증 (건너뛰지 말 것 — 통과 전엔 발행 켜지 않는다)

`threads/harvester.py::parse_feed()` 는 **코디네이터가 손으로 지어낸 합성 HTML
픽스처**로만 검증됐습니다(`tests/fixtures/feed_page.html`). 실제 Threads 페이지와 한
번도 대조된 적이 없고, 리뷰에서 이미 "글이 조용히 통째로 드롭되거나(중첩 카드) 엉뚱한
글에 답글이 오귀속되는(멘션 링크 오귀속)" 모양이 실제로 발생함을 확인했습니다(수정은
됐지만, 그 수정이 실제 Threads 마크업에도 맞는지는 아직 아무도 안 봤습니다).
**이 단계를 통과하기 전에는 자동 발행(6·7단계)을 켜지 마세요.**

절차:
1. Chrome 에서 로그인된 상태로 Threads 추천 피드를 열고, 개발자도구(F12) →
   Elements 에서 피드 컨테이너를 우클릭 → **Copy → Copy outerHTML** 로 저장
   (`captured.html` 등으로 UTF-8 저장).
2. 아래 9개 항목을 실제로 하나씩 확인합니다(상세 배경·왜 이게 위험한지는
   `D:\.superpowers\sdd\2026-08-03-threads-reply-ad\task-4-report.md` 의
   "6. 실측 체크리스트" 참고):
   1. **카드 경계** — `data-pressable-container="true"` 개수(Ctrl+F)가 화면에
      보이는 글 개수와 맞는지. 리포스트/인용 카드는 이 속성이 중첩되는지.
   2. **카드 자신의 permalink 구조** — 카드 하나를 열어, `<a href="/@handle/post/id">`
      바로 뒤에 (공백만 두고) `<time datetime="...">` 가 바로 오는지. 아이콘/래퍼가
      끼어 있으면 그 카드는 조용히 드롭됩니다(사고는 아니지만 수집률이 이유 없이
      낮아 보이는 원인).
   3. **앵커 속성 순서** — 그 `<a>` 태그에서 `href` 가 `role`/`class`/`aria-*`/`data-*`
      뒤에 오는 경우가 있는지(React 렌더링에서 흔함). 여기 걸리면 **로그는 다 정상으로
      보이는 채로 수집이 통째로 0건**이 되는, 가장 알아채기 어려운 실패 모양입니다.
   4. **짝 유일성(검산)** — 아래 명령으로 화면상 카드 수와 파싱 결과가 맞는지 확인:
      ```bash
      python -c "
      from threads import harvester
      html = open('captured.html', encoding='utf-8').read()
      posts = harvester.parse_feed(html)
      print('parsed:', len(posts))
      print('ambiguous(모호-버려짐):', harvester.last_ambiguous_count())
      print('no_pairing(짝 없음, 광고/UI 포함):', harvester.last_no_pairing_count())
      "
      ```
      `parsed + ambiguous + no_pairing`(+ 화면에서 눈으로 확인한 중복 글 수)이
      화면상 카드 수와 같아야 합니다. 안 맞으면 카운터 중 하나가 실패를 놓치고
      있다는 뜻입니다.
   5. **작성자 = URL 핸들** — 화면에 보이는 작성자 이름이 permalink 의 `/@handle/`
      부분과 항상 일치하는지(닉네임 표시와 다를 수 있음).
   6. **시각 포맷** — `<time>` 의 `datetime` 속성이 항상 있고 `YYYY-MM-DDTHH:MM:SS`
      로 시작하는 형식인지(`THREADS_POST_MAX_AGE_MIN` 필터가 이 형식을 전제합니다).
   7. **본문 스팬 범위** — `dir="auto"` 스팬에 해시태그 칩·링크 미리보기 제목·
      좋아요/댓글 수 같은 게 섞이는지(섞이면 얼마나 자주인지), 반대로 정상 문장이
      실수로 걸러지지는 않는지.
   8. **id 안전 문자** — 실제 post id 에 `?`/`#` 외의 특수문자(인코딩된 공백 등)가
      낄 수 있는지.
   9. **비-사용자 카드** — 광고/추천계정 카드가 피드에 섞여 있는지(4번 검산의
      "화면상 카드 수"에 포함할지 미리 정해야 합니다).
3. 9개 전부 확인 후 문제가 있으면(특히 3·4번에서 수집이 비정상적으로 낮게 나오면)
   `threads/harvester.py` 의 정규식을 실측한 마크업에 맞게 고치고 `tests/test_harvester.py`
   회귀 테스트를 다시 돌린 뒤 처음부터 재검증하세요.

### 5. 골든셋 실측 — 자동 발행 임계값(THREADS_AUTO_THRESHOLD) 확정

`THREADS_AUTO_THRESHOLD` 는 지금 실측 근거가 없는 기본값(90점)입니다 — 이 프로젝트에서
`login.py threads` 가 실행된 적이 없어(이제 1단계로 생겼습니다) 실제 라벨링 데이터가
없었기 때문입니다. 절차(상세는
`D:\.superpowers\sdd\2026-08-03-threads-reply-ad\task-8-report.md` 와 설계서
`docs/superpowers/specs/2026-08-03-threads-reply-ad-design.md` 7-1절 참고):

1. **수집**: 1단계에서 만든 세션으로 실제 추천 피드 100건 이상 수집
   (`threads.harvester.harvest(limit=120)`).
2. **라벨링**: 각 건에 `reply`(달아야 함)/`skip`(절대 달면 안 됨)/`borderline`(애매함)
   을 **사장님이 직접** 판단해 채웁니다. `skip` 최소 50건, 그중 하드블록 계열
   (부고·사고·질병·정치) **15건 이상**.
   - **여기에 반드시 추가할 것 — 하드블록 단어가 하나도 없는 "완곡한 위험 게시물"**.
     예를 들어 다음 문장은 `부고`/`사망`/`삼가`/`명복` 같은 하드블록 리터럴이
     **전혀 없어** 키워드 단계를 그대로 통과해 LLM 까지 갑니다(직접 확인됨):
     > "할아버지가 하늘로 떠나셨어요 마지막으로 함께 찍은 사진 정리하고 있어요"

     이런 문장에는 `gate.screen()` 의 LLM 판정이 **유일한 방어선**입니다 — 지금까지
     쓴 하드블록 불변식 테스트(`tests/test_gate_golden.py`)는 "하드블록 키워드가
     실제로 들어 있는 글"만 검증했고, 이런 완곡 표현은 어떤 테스트도 커버하지
     않습니다. **최소 5건 이상**, 부고·질병·사고를 완곡하게 표현하되 하드블록
     단어는 전혀 안 쓰는 문장을 `skip` 라벨로 골든셋에 넣고, LLM 이 실제로
     걸러내는지 확인하세요. 하나라도 통과(고득점)하면 그 카테고리의 완곡
     표현 패턴을 프롬프트(`threads/prompts/screen.txt`)에 보강해야 합니다.
3. `tests/fixtures/sample_posts.json` 의 `posts` 배열을 라벨링한 실제 데이터로
   교체하고, 각 항목의 `"synthetic": true` 를 지우거나 `false` 로 바꿉니다.
4. 실측 실행:
   ```bash
   python tools/threads_goldenset.py
   ```
   출력에 `SYNTHETIC DATA WARNING` 이 더 이상 뜨지 않으면 실측이 유효하게 성립한
   것입니다.
5. **판정 기준 — 오탐(false positive) 이 단 1건이라도 있으면 자동 발행은 켜지
   않습니다.** (`skip` 인데 `THREADS_GATE_THRESHOLD` 이상 득점한 글이 1건이라도
   있다는 뜻입니다.) 오탐이 있으면 `threads/prompts/screen.txt` 와
   `profiles/*.yaml` 의 `hard_block` 을 보강하고 2~5 를 처음부터 반복하세요.
   오탐 0건은 자동 발행을 켜는 **필요조건**이지 충분조건이 아닙니다 — 6단계도
   반드시 통과해야 합니다.
6. 오탐 0건이면 리포트가 제시하는 `skip 최고점 + 10`(최소 85) 을
   `THREADS_AUTO_THRESHOLD` 후보로 채택합니다. 다음 단계에서 `.env` 에 실제로
   반영합니다(반영하지 않으면 기본값 90 이 그대로 쓰입니다).

### 6. 승인 전용 운영부터 — 자동 발행은 아직 끈 채

`.env` 를 아래처럼 설정:
```bash
THREADS_ENABLED=1
GLOBAL_DRY_RUN=0
THREADS_AUTO_THRESHOLD=101      # 100점 만점 밖 값 — 자동 발행은 켜지지 않는다
```
`service.py` 를 (재)시작하면 45분 간격으로 회차가 자동으로 돌기 시작합니다(꺼져
있으면 등록조차 안 됨 — 아래 "쓰레드 회차와 service.py" 참고). 임계값을 101로 둔
동안은 모든 통과 건이 승인 큐로만 쌓입니다.

- `/approvals` 에서 최소 **30건** 처리하며 승인률을 확인하세요.
- **승인률이 낮으면(대략 70% 미만) 7단계로 넘어가지 마세요.** 5단계로 돌아가
  프롬프트/하드블록을 보강한 뒤 반복합니다. 자동 발행은 "사람이 봤으면 승인했을
  것"이 전제이므로, 승인률이 그 전제의 유일한 증거입니다.

### 7. 자동 발행 켜기

`.env` 에 5단계에서 채택한 임계값을 **문자 그대로** 반영(예시이지 그대로 쓰는 숫자가
아닙니다 — 5단계 리포트가 제시한 실제 숫자를 넣으세요):
```bash
THREADS_AUTO_THRESHOLD=85
THREADS_AUTO_DAILY_LIMIT=3
```
`service.py` 재시작. 1주 무사고면 `THREADS_AUTO_DAILY_LIMIT` 을 단계적으로 올리세요.

### 8. 첫 실제 동작은 반드시 사람이 지켜본다

`threads/publisher.py` 의 캡차 감지 문구와 답글 삭제 클릭 순서는 **실제 Threads
화면을 대상으로 한 번도 검증된 적이 없습니다**(합성 테스트로만 확인됨). 자동 발행이
켜진 뒤 **첫 실제 게시 1건, 첫 실제 삭제 1건**은 화면을 사람이 지켜보는 채로
진행하세요(가능하면 `/dashboard` 를 같이 열어 `posts` 기록도 같이 확인).

**잘못 나간 답글을 지우는 법:**
```bash
python -c "
from threads.publisher import ThreadsPublisher
pub = ThreadsPublisher('<계정명>')
pub.login()
print(pub.delete_reply('<잘못 나간 답글 URL>', dry_run=False))
pub.quit()
"
```
`dry_run=False` 를 반드시 명시하세요(기본값은 `True`라 안 지정하면 실제로 안
지워집니다). `/dashboard` 에서 답글 URL 을 먼저 확인하세요.

### 9. 비상 정지

`.env` 에서 한 줄:
```bash
THREADS_ENABLED=0
```
**주의 — 이 값은 `service.py` 프로세스가 시작할 때 한 번만 읽습니다.** `.env` 만
고치고 이미 떠 있는 `service.py` 를 그대로 두면 **즉시 멈추지 않습니다.** 확실히
끄려면 둘 중 하나를 하세요:
- `.env` 를 고친 뒤 `service.py` 를 재시작한다(새 프로세스는 `THREADS_ENABLED=0` 을
  읽고 회차 등록 자체를 건너뜁니다), 또는
- 지금 당장 멈춰야 하면 떠 있는 `service.py` 창을 **Ctrl+C**(또는 작업 관리자에서
  프로세스 종료)로 그냥 꺼버리세요 — 재시작 없이도 확실히 멈춥니다.
- (참고: 수집이 3회 연속 0건이면 `service.py` 가 이 스위치를 **스스로도** 끕니다 —
  아래 "쓰레드 회차와 service.py" 참고. 그 경우도 `.env` 파일 자체는 안 바뀝니다.)

**이 스위치가 멈추는 것**: 다음 `service.py` 재시작부터의 회차 등록, 진행 중이던
루프의 다음 반복부터의 회차 실행. **멈추지 않는 것**: 이미 나간 답글(사람이 직접
지워야 함 — 위 8단계 명령과 동일), 이미 승인 큐에 쌓인 대기 건(그대로 남고, 처리
여부는 `/approvals` 에서 사람이 결정).

### 쓰레드 회차와 service.py (동작 원리 — 참고)

- `service.py` 는 APScheduler 가 아니라 subprocess 감독 루프입니다. 쓰레드 회차는
  `service.py` 자신의 프로세스 안에서 도는 **전용 백그라운드 스레드**로 처리됩니다
  (감독 루프 안에서 동기 실행하면, 실발행 중 답글 사이 대기(180~600초)까지 더해져
  회차 하나가 몇 분씩 걸릴 수 있어 autoad/loanapp/sync 재시작 감지가 그만큼 멈추기
  때문입니다).
- `THREADS_ENABLED=0` 이면 이 스레드는 **등록조차 되지 않습니다**(로그에
  `[threads] THREADS_ENABLED=0 - 답글 회차를 등록하지 않습니다` 한 줄만 남고 끝).
  꺼진 기능이 45분마다 로그를 채우는 일은 없습니다.
- 회차마다 수집 건수와 함께 `harvest_ambiguous`(파싱 모호로 버려진 카드)·
  `harvest_unpaired`(permalink+시각 짝이 아예 없는 카드 — 광고/UI 카드도 섞이므로
  이 값 자체가 크다고 무조건 사고는 아닙니다)를 `data/logs/service.log` 에 남깁니다.
- **3회 연속 수집 0건**이면 서비스가 "셀렉터가 깨졌다고 의심"하는 로그를 남기고
  그 프로세스 안에서 `THREADS_ENABLED` 를 스스로 끕니다(`.env` 파일은 안 바뀜).
  원인(대개 Threads 마크업 변경 — 3단계로 돌아가 재검증)을 해소한 뒤 `service.py`
  를 재시작하면 다시 등록됩니다.

### 알려진 한계 (운영자가 알고 있어야 하는 것)

- **파서가 실제 Threads 마크업으로 검증된 적이 없습니다** — 3단계를 반드시 거쳐야
  하고, 3단계를 통과했더라도 Threads 가 마크업을 바꾸면(흔한 일입니다) 다시 깨질 수
  있습니다. 그 신호가 바로 "3회 연속 수집 0건 자동 정지"입니다.
- **하드블록 매칭은 일부러 과차단합니다.** 예: `사고` 라는 단어가 있으면 "사고
  현장"뿐 아니라 "새 폰카 **사고** 싶은데"도 막힙니다. 매출 기회를 일부 잃더라도
  안전을 우선한 설계 선택입니다(2라운드 리뷰에서 좁히려다 실패해 다시 넓힌
  이력이 있습니다 — task-8-report.md 참고).
- **캡차 감지는 완벽하지 않습니다.** `threads/publisher.py` 는 "답글 입력창이
  없다"는 구조적 신호와 캡차 문구를 **같이** 봐야만 캡차/차단 화면으로 판정합니다.
  챌린지 화면이 우연히 입력창처럼 생긴 요소를 보여주면 이 감지를 조용히 우회합니다
  — 실제로 이런 화면을 본 적이 없어 검증되지 않았습니다(8단계에서 사람이 지켜봐야
  하는 이유 중 하나).
- **계정 쿨다운은 답글이 실제로 게시에 성공했을 때만 시작합니다.** 드라이런이나
  실패는 쿨다운을 걸지 않습니다 — 의도된 동작이지만, "여러 번 시도했는데 왜
  같은 작성자에게 또 답글이 붙지" 라고 헷갈릴 수 있어 기록해 둡니다.
